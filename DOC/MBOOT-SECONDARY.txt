=======================================================

Goal
----
Keep m-boot's existing firmware boot and UNMODIFIED runner-compatible
GRUB core and module set. Load any necessary customized Ventoy functionality
as a version-matched GRUB .mod, not as a rebuilt or patched GRUB core. If
a UEFI virtual-CD mechanism is required, its Ventoy .efi application is a
SEPARATE EFI executable, not the same thing as the GRUB .mod. Do not install
Ventoy2Disk to the m-boot disk.

Operator's confirmed original-Ventoy result
-------------------------------------------
The original Ventoy distribution has already booted the actual TrueNAS and
Proxmox ISO images in the operator's environment. Do not rerun that baseline
test merely to rediscover ISO compatibility; the remaining target is the
secondary chainload from m-boot's disk layout.

m-boot simplification target (not yet implemented)
-------------------------------------------------
Keep the full Ventoy ISO compatibility and kernel-handoff engine, but do
not require the operator to install a Ventoy-branded disk, keep an ISO
on a special Ventoy partition, or create .vlnk descriptors for ISO files
on another disk. m-boot may use its usual GPT 2 ESP and GPT 3 ext4 data
partition for a DEFAULT local ISO directory; these are not requirements
for the ISO engine or for an explicitly selected image elsewhere.

In the optional m-boot secondary mode:
- Identify the chosen ISO by its actual accessible GRUB device/partition
  and file path, including files on other disks; validate that file and
  the sector mappings needed for kernel/OS handoff, not Ventoy branding.
- Keep bootloader resources separate from ISO file location; preserve
  existing standard-Ventoy identity/layout checks only for standard mode.
- Treat the .vlnk and fake-vlnk path redirect as legacy compatibility
  routing, not the target primary mechanism for selecting external ISO.
- Preserve data needed by Ventoy's image sector mapping and OS parameter
  handoff, including the ISO's real disk signature and partition identity.

Current mismatch: the secondary fork still validates p2 MBOOTESP/p3
MBOOTDATA in ventoy_check_mboot_device(), calculates default cached
partition sizes from fixed GPT indexes, and uses vtoy_iso_part and
vt_set_fake_vlnk in menu/boot paths. The port probes do NOT yet remove
those dependencies. Avoid disabling them alone without real image-source
tracking and boot validation.

Required disposable UEFI acceptance: boot an ISO from normal /m/boot/iso,
then from an arbitrary readable path/partition and another attached disk
without a .vlnk; confirm the OS finds the selected ISO after kernel
handoff. Confirm missing/inaccessible ISO fails safely. Re-test ordinary
Ventoy disk layout checks in standard mode; never use physical USB for
experiments.

Experimental layout of the SECONDARY application on GPT 2:
    /ventoy-secondary/EFI/BOOT/grubx64_real.efi
    /ventoy-secondary/grub/...
    /ventoy-secondary/ventoy/...
    /ventoy-secondary/tool/...

Do not overwrite /EFI/BOOT/BOOTX64.EFI or /m/boot/loader on MBOOTESP.
These paths are *target staging paths*, not files created by this patch.

Implemented source adaptations on the experimental branch
----------------------------------------------------------
- GRUB2/MOD_SRC/grub-2.04/install.sh accepts the optional environment
  variable VENTOY_GRUB_PREFIX, with unchanged upstream default '(,2)/grub'.
  When building the secondary image, select:
      VENTOY_GRUB_PREFIX='(,2)/ventoy-secondary/grub'
  This is a GRUB build option, not a runtime setting of an existing EFI file.
- INSTALL/grub/grub.cfg recognizes m-boot's ESP loader marker and the ISO
  directory on GPT 3, selects GPT 3 for image enumeration, and confines
  default image search to /m/boot/iso. Ordinary Ventoy stays GPT 1 / GPT 2.
- grub-core/ventoy/ventoy_cmd.c separately validates the labeled FAT32 ESP
  and ext4 data volumes for the opt-in alternative, preserves upstream's
  original-device checks for normal Ventoy, and handles the 32 MiB size
  assumption when the alternate layout has been positively verified.
  In verified secondary mode it reads ventoy_efiboot.img.xz from
  /ventoy-secondary/ventoy/ and loads checksum.cfg from the GRUB prefix
  /ventoy-secondary/grub/. Standard Ventoy asset paths stay unchanged.
- The Ventoy EFI application's ISO9660/UDF driver paths select the nested
  /ventoy-secondary/ventoy/ directory only for the m-boot opt-in.

Current no-core development route (decision 2026-11-03)
--------------------------------------------------------
The operator rejects rebuilding GRUB core as a dependency for m-boot's
ISO engine. The previous full-GRUB source-delta workflow and patched-core
prototype are DIAGNOSTIC HISTORY, not the intended build or release
strategy. The branch's GRUB2/MOD_SRC/grub-2.04 overlay is evidence of
what Ventoy changed, NOT a GRUB core patch to be deployed.

1. Compile only GRUB .mod code against the exact Ubuntu runner GRUB source
   and ABI; retain the existing m-boot GRUB binary and standard modules.
   Probe GRUB2/port/probe-source.c with
   .github/workflows/probe-standalone-ventoy-module.yml. This temporary
   diagnostic module reads source device, partition, filesystem and file
   size by standard grub_file_open; it is NOT an ISO boot implementation.
   Build/make generation must not compile or patch GRUB kernel/core.
2. Load the resulting .mod dynamically with the unchanged m-boot GRUB
   in a disposable UEFI QEMU test. Then verify an ACTUAL bootable ISO on
   the normal data partition and on a second virtual disk without VLNK.
   The completed diagnostic test below is a precursor using an unmodified
   Ubuntu GRUB image and a non-bootable file named .iso; the m-boot
   integration, ISO boot and installer mount remain pending.
3. Rework the existing Ventoy module by deleting fake VLNK routing and
   callers that use .vlnk suffix recognition to synthesize a same-partition
   image path. Identify the selected ISO by its REAL openable GRUB
   device/partition/path. Keep device/FS identification and required
   image sector maps for the OS handoff. Do not replace lost APIs with
   fake data or empty stub implementations.
4. Investigate whether standard GRUB disk read hooks, filesystem APIs,
   EFI page allocation and file filters suffice for the remaining
   Ventoy functions. Retain the separate EFI virtual-CD application ONLY
   if testing shows its functionality is necessary; it is not a module
   dynamically loaded by insmod. Report unsupported core ABI assumptions
   instead of reintroducing GRUB core patches.
5. If maintaining a generic ISO engine demands a growing collection of
   installer-specific quirks, evaluate a simpler route for the actual
   Proxmox and TrueNAS installation images: boot kernel and initramfs from
   GRUB loopback and, only if required, add a small repeatable initramfs
   adapter for finding the backing ISO. Compare on real disposable QEMU
   tests before selecting it. Do not modify original ISO bytes by default.
6. Never release a partial proof as Ventoy; only release a tested m-boot
   integration after module load, ISO boot, installer/root mounting and
   cross-disk handoff validation. No physical USB writes are authorized.

Observed dependencies:
- ventoy_check_file_exist() is only formatted-path grub_file_open/close;
  it needs no special GRUB core support.
- grub_file_is_vlnk_suffix() recognizes alias names; the patched
  grub_file_open() resolves aliases and sets file->vlnk. Such aliases
  are an optional workaround for Ventoy's fixed-image-path design,
  NOT an intrinsic requirement of a UEFI ISO image or GRUB.
- Ventoy's file->read_hook/disk-hook and filesystem extent helpers build
  physical sector mappings used during EFI and post-kernel handoff; do
  NOT discard them without replacing their role correctly.
- Ventoy's EFI app already reads the selected disk metadata/sector list.
  On non-GPT disks it may apply an additional legacy-Ventoy layout check;
  that must not become an m-boot restriction.
- Stock GRUB file filters exist; Ventoy already registers one using the
  standard grub_file_filter_register. GRUB menu hotkeys/themes are optional
  to the image boot engine, not reasons to patch the core.
- No standalone/full Ventoy module has been proven boot-capable yet.

Real fragmented ISO extent-mapping proof (2026-11-03)
--------------------------------------------------
- On experimental fork branch, GRUB2/port/probe-extents.c implements
  vt_extent_probe in the existing dynamically loaded source-probe .mod.
  It validates a real ISO9660 primary volume descriptor, reads the file
  through stock GRUB filesystem APIs with the exact 2.12 disk read-hook
  ABI, merges contiguous byte ranges and reports logical ISO offsets
  and absolute disk offsets. There are no GRUB core edits and no VLNK.
  This remains DIAGNOSTIC code, not the Ventoy chainloader.
- The hook's sector argument is ALREADY an absolute whole-disk sector
  in tested GRUB 2.12; do not add the GPT start LBA again. The first
  fragmented test showed a false one-partition offset; our independent
  raw-GPT verifier rejected it. GRUB2/port/verify-extent-map.py checks
  each reported physical byte range is inside the actual GPT partition
  and byte-equal to the original ISO; all mapped byte ranges must cover
  the entire image in order and have at least one physical discontinuity.
- QEMU fixture is a true ISO9660 filesystem produced by xorriso with
  deterministic nonuniform content. A and C filler plus a tail-filling
  file deliberately force the ISO to occupy two noncontiguous extents
  on the SECOND GPT disk. The ISO has no bootloader and has not been
  booted; it is NOT a Proxmox or TrueNAS installation image.
- GitHub Actions run 41617152860 at fork SHA
  dc6acc482208754e4637814dab036e309012ab40 PASSED. GRUB .mod
  compiled against runner GRUB 2.12-1ubuntu7.3 without compiling or
  patching core, OVMF booted standard GRUB, and insmod loaded it.
  Independent reconstruction verified ISO=2,471,936 bytes, two extents,
  one discontinuity, every byte equal, matching raw-disk and source
  SHA-256 d81a159af3486d48009fff44497631de3163eef350eecf47861b7d8ec97d7ef3.
  No physical disk was used. Neither m-boot main nor Ventoy master changed.
- Test scope: one true ISO9660 filesystem on FAT32 on an extra GPT
  virtual disk. No ext4/exFAT, sparse-file handling, large multi-GB ISO,
  EFI virtual CD or installer/root mount is validated yet. The mapper
  returns byte extents rather than Ventoy's final firmware-sector-map
  ABI; compatibility conversion and OS handoff remain open.
