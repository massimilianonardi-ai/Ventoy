m-boot secondary UEFI integration — experimental fork work
=======================================================
Status: GRUB 2.12 partial module compile probes, NOT a full build or boot test
Base: ventoy/Ventoy master 74cff34240dca6991b79c6656770670da7b0c39e

Goal
----
Keep m-boot's existing firmware boot and GRUB menu. Chainload an independent
Ventoy GRUB EFI application only for ISO images that require Ventoy's
compatibility mechanisms. Do not install Ventoy2Disk to the m-boot disk.

Operator's confirmed original-Ventoy result
-------------------------------------------
The original Ventoy distribution has already booted the actual TrueNAS and
Proxmox ISO images in the operator's environment. Do not rerun that baseline
test merely to rediscover ISO compatibility; the remaining target is the
secondary chainload from m-boot's disk layout.

Existing m-boot disk after operator provisioning
------------------------------------------------
GPT 1: BIOS Boot
GPT 2: FAT32, label MBOOTESP, 512 MiB (m-boot primary boot files)
GPT 3: ext4, label MBOOTDATA, contains /m/boot/iso/

m-boot simplification target (not yet implemented)
-------------------------------------------------
Keep the full Ventoy ISO compatibility and kernel-handoff engine, but do
not require the operator to install a Ventoy-branded disk, keep an ISO
on a special Ventoy partition, or create .vlnk descriptors for ISO files
on another disk. m-boot may use its usual GPT 2 ESP and GPT 3 ext4 data
partition for a DEFAULT local ISO directory; these are not requirements
for the ISO engine or for an explicitly selected image elsewhere.

In the optional m-boot secondary mode:
- Identify the chosen ISO by its actual accessible GRUB device/partition
  and file path, including files on other disks; validate that file and
  the sector mappings needed for kernel/OS handoff, not Ventoy branding.
- Keep bootloader resources separate from ISO file location; preserve
  existing standard-Ventoy identity/layout checks only for standard mode.
- Treat the .vlnk and fake-vlnk path redirect as legacy compatibility
  routing, not the target primary mechanism for selecting external ISO.
- Preserve data needed by Ventoy's image sector mapping and OS parameter
  handoff, including the ISO's real disk signature and partition identity.

Current mismatch: the secondary fork still validates p2 MBOOTESP/p3
MBOOTDATA in ventoy_check_mboot_device(), calculates default cached
partition sizes from fixed GPT indexes, and uses vtoy_iso_part and
vt_set_fake_vlnk in menu/boot paths. The port probes do NOT yet remove
those dependencies. Avoid disabling them alone without real image-source
tracking and boot validation.

Required disposable UEFI acceptance: boot an ISO from normal /m/boot/iso,
then from an arbitrary readable path/partition and another attached disk
without a .vlnk; confirm the OS finds the selected ISO after kernel
handoff. Confirm missing/inaccessible ISO fails safely. Re-test ordinary
Ventoy disk layout checks in standard mode; never use physical USB for
experiments.

Experimental layout of the SECONDARY application on GPT 2:
    /ventoy-secondary/EFI/BOOT/grubx64_real.efi
    /ventoy-secondary/grub/...
    /ventoy-secondary/ventoy/...
    /ventoy-secondary/tool/...

Do not overwrite /EFI/BOOT/BOOTX64.EFI or /m/boot/loader on MBOOTESP.
These paths are *target staging paths*, not files created by this patch.

Implemented source adaptations on the experimental branch
----------------------------------------------------------
- GRUB2/MOD_SRC/grub-2.04/install.sh accepts the optional environment
  variable VENTOY_GRUB_PREFIX, with unchanged upstream default '(,2)/grub'.
  When building the secondary image, select:
      VENTOY_GRUB_PREFIX='(,2)/ventoy-secondary/grub'
  This is a GRUB build option, not a runtime setting of an existing EFI file.
- INSTALL/grub/grub.cfg recognizes m-boot's ESP loader marker and the ISO
  directory on GPT 3, selects GPT 3 for image enumeration, and confines
  default image search to /m/boot/iso. Ordinary Ventoy stays GPT 1 / GPT 2.
- grub-core/ventoy/ventoy_cmd.c separately validates the labeled FAT32 ESP
  and ext4 data volumes for the opt-in alternative, preserves upstream's
  original-device checks for normal Ventoy, and handles the 32 MiB size
  assumption when the alternate layout has been positively verified.
  In verified secondary mode it reads ventoy_efiboot.img.xz from
  /ventoy-secondary/ventoy/ and loads checksum.cfg from the GRUB prefix
  /ventoy-secondary/grub/. Standard Ventoy asset paths stay unchanged.
- The Ventoy EFI application's ISO9660/UDF driver paths select the nested
  /ventoy-secondary/ventoy/ directory only for the m-boot opt-in.

Safe test sequence (not yet executed)
-------------------------------------
1. Run .github/workflows/probe-secondary-grub.yml on the named
   ubuntu-24.04 GitHub runner. It records the actual distribution GRUB
   packages and verifies a stock GRUB EFI baseline; it does NOT compile
   or release Ventoy. The discovered versions are provenance, not pins.
2. Use .github/workflows/port-runner-grub.yml to diagnose the complete
   patch gap against distribution GRUB source. It compares upstream 2.04
   solely as the historical reference, not as the selected build version.
   The resulting patch is diagnostic, NOT a release build input.
3. Use .github/workflows/probe-ventoy-module.yml to compile only the
   unported Ventoy module against the runner source. It applies
   GRUB2/port/runner-efi-api.patch, runner-browser-api.patch and
   runner-file-api.patch to a temporary GRUB tree. The patches port
   initial EFI GUID/variable, browser and real file-size APIs, but the
   experiment still lacks other GRUB core ABI integrations: a failure
   is an expected evidence boundary, not permission to publish its output.
4. Finish porting the Ventoy GRUB core and custom module to the actual
   runner-matched GRUB sources. Rebuild matching GRUB tools and modules
   with VENTOY_GRUB_PREFIX='(,2)/ventoy-secondary/grub'.
   Original GRUB2/buildgrub.sh and MOD_SRC/grub-2.04/ remain legacy
   upstream reference, NOT a secondary release build route.
5. Build the modified EDK2 Ventoy UEFI application too. Unmodified
   ventoy_x64.efi does not contain the relocated ISO driver paths.
6. Stage same-build Ventoy resources under /ventoy-secondary/ in a
   disposable QEMU disk only, preserving m-boot's EFI fallback and loader.
7. With Secure Boot disabled in OVMF, chainload
   /ventoy-secondary/EFI/BOOT/grubx64_real.efi from m-loader.
8. Verify secondary GRUB initialization, m-boot GPT detection, ISO
   enumeration, UEFI ISO chainload and kernel/live-root mount. Also check
   the changed fork on a disposable standard Ventoy GPT layout.

Known limits / do not claim yet
-------------------------------
- GitHub Actions source-compile probe `41600842303` applied all three
  temporary GRUB 2.12 port patches, then failed compiling remaining
  incompatible Ventoy GRUB core API calls (EFI buffer, virtual-link,
  filesystem/blocklist, GRUB exit and GUID interfaces). This is NOT
  a successful Ventoy module build, firmware boot or release artifact.
- No successful custom Ventoy GRUB compilation/build, OVMF run, kernel
  handoff, ARM64 boot, Secure Boot chain or physical USB test has been
  obtained for this branch. A stock-runner GRUB probe is not such a build.
- GRUB 2.04 is no longer the chosen build/release version; the old Ventoy
  overlay cannot be linked with current Ubuntu GRUB without a source port.
  Use a named runner OS image, not ubuntu-latest, and record actual package
  versions and source provenance for every future release.
- Upstream distribution packaging creates a VTOYEFI image at the standard
  partition-root layout; a separate staging/export procedure will be needed
  for the nested m-boot path. It does not appear automatically after build.
- Upstream code may still contain other partition-number or filesystem
  assumptions in the Linux/initramfs handoff and boot-specific handlers;
  these remain to be identified through an actual boot and targeted review.
- No change to m-boot product or the operator's real USB is authorized or
  made in this source-only work unit.
- Ventoy's upstream GPLv3 license and corresponding source obligations
  continue to apply to modified redistributions.
